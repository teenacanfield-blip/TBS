# Turning on accounts and live reviews

Right now reviews are saved in each visitor's own browser. Nobody else sees
them. This guide switches that over to real accounts and real live reviews that
everyone can read.

The website itself cannot do this on its own. It is just files on GitHub Pages —
there is no computer of yours running anywhere to remember things. Supabase is
that missing piece: a free database with accounts built in.

> **An adult should do steps 1–3.** Making the Supabase account needs an email
> address, and once this is switched on you are storing other people's email
> addresses. There is a short section at the bottom about what that means.

Steps 1–4 happen once. After that it just works.

---

## 1. Make the Supabase project

1. Go to <https://supabase.com> and sign up. The free plan is plenty — it allows
   far more accounts and reviews than this site will ever see.
2. Click **New project**. Name it anything (`thirsty-bear` is fine).
3. It asks for a **database password**. Save it somewhere safe. You will not need
   it for this guide, but you cannot get it back later.
4. Pick the region closest to you and create it. It takes a minute or two to
   finish setting up.

## 2. Copy the two values into the site

In the Supabase dashboard: **Project Settings → API**. You need two things:

| On the Supabase page | Goes into `supabase-config.js` |
| --- | --- |
| **Project URL** | `url` |
| **anon** **public** key (the long one) | `anonKey` |

Open `supabase-config.js` at the top of this folder and paste them in:

```js
const SUPABASE = {
  url: 'https://YOUR-PROJECT.supabase.co',
  anonKey: 'eyJhbGciOi...the long one...',
};
```

> **Only ever the `anon` `public` key.** There is another one on that page called
> `service_role`. That key ignores every security rule. If it went into this file
> it would be published on the website, and anyone could wipe the database.
> The `anon` key is *designed* to be public — step 3 is what makes that safe.

## 3. Paste in the database and its rules

In the dashboard: **SQL Editor → New query**. Paste all of this in and press
**Run**. It makes the two tables and locks them down.

```sql
-- Who everyone is. One row per account, holding the public username.
create table public.profiles (
  id       uuid primary key references auth.users on delete cascade,
  username text unique not null,
  created  timestamptz default now()
);

-- The reviews themselves.
create table public.reviews (
  id         bigint generated by default as identity primary key,
  user_id    uuid not null references public.profiles(id) on delete cascade,
  game_key   text not null,
  stars      int  not null check (stars between 1 and 5),
  text       text not null default '' check (char_length(text) <= 600),
  created_at timestamptz default now(),
  -- One review per person per game. Posting again replaces nothing; they must
  -- delete the old one first, which stops a single person flooding a page.
  unique (user_id, game_key)
);

-- When someone signs up, make their profile row automatically using the
-- username they typed. Doing it here rather than in the browser means a profile
-- cannot be skipped or faked.
create function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = '' as $$
begin
  insert into public.profiles (id, username)
  values (new.id, new.raw_user_meta_data->>'username');
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute procedure public.handle_new_user();

-- Row Level Security. THIS is what makes the public anon key safe: without
-- these rules on, anyone could read and write anything.
alter table public.profiles enable row level security;
alter table public.reviews  enable row level security;

-- Usernames are public, so reviews can show who wrote them.
create policy "usernames are readable"
  on public.profiles for select using (true);

-- You may only ever touch your own profile row.
create policy "own profile is editable"
  on public.profiles for update using (auth.uid() = id);

-- Everyone can read every review, signed in or not.
create policy "reviews are readable"
  on public.reviews for select using (true);

-- You may only post a review as yourself.
create policy "post your own review"
  on public.reviews for insert with check (auth.uid() = user_id);

-- You may only delete your own review.
create policy "delete your own review"
  on public.reviews for delete using (auth.uid() = user_id);
```

## 4. Check the email settings

**Authentication → Sign In / Providers → Email.** Make sure **Confirm email** is
on. That is the whole point of asking for an email: it means an account belongs
to someone who can actually receive mail there, which makes junk accounts a lot
more effort.

Supabase's built-in mail is rate limited to a handful of messages an hour. That
is fine for friends and family. If the site ever gets busy, the same page lets
you plug in a proper mail service.

## 6. Test it

On the live site, open any game and scroll to Reviews. You should see **Create an
account**. Make one with a real email, click the link in the email, sign in, and
post a review. Then open the site on your phone, or in a private window, and the
review should be sitting there.

## What you have signed up for

Once this is on, you are keeping other people's email addresses. That is a real
responsibility and it is worth knowing what it involves.

**You can see and delete anything.** Supabase dashboard → **Table Editor** →
`reviews`. Deleting a row removes the review from the site immediately. Same for
`profiles` and, under **Authentication → Users**, whole accounts.

**Nobody's password is stored by you.** Supabase hashes them and never hands
them back — not even to you. This site never sees a password after it is typed.
That is exactly why we are not hand-rolling the accounts.

**Emails are never shown on the site.** Reviews display the username only. The
email is used for the confirmation link and nothing else.

**If someone asks you to delete their account,** do it — delete their row in
`profiles` and their user under Authentication → Users. Their reviews go with it
automatically.

**Moderation is on you.** Anyone with a confirmed email can post. If the site
goes anywhere public, check it now and then.

## If something is wrong

**The sign-in box never appears.** `supabase-config.js` is still empty, or the
values have a typo. Open the site, press F12, and look at the Console tab.

**"Could not load reviews".** Usually step 3 was not run, or was only half run.
Re-run the whole SQL block — it is safe to run again after deleting the tables.

**Sign-up works but the review says permission denied.** Row Level Security is on
but the policies did not get created. Re-run the policy half of step 3.

**No confirmation email arrives.** Check spam. Supabase's built-in mail is rate
limited — if you have made several test accounts quickly, wait an hour.

**"That username is taken"** and you are sure it is not — usernames are kept in
`profiles`, so look there. A half-finished test signup can leave one behind.
