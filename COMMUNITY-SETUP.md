# Turning on the Community area

The Community tab is built and sitting in the site right now. Until the steps
below are done it says so plainly and nothing else changes.

When it is on:

- People sign in — one tap with a Google account, or an email and password.
- They put a game up by pasting a link to it.
- **Nothing appears until you approve it.** Submissions go into a queue only you
  can see.
- Approved games show in the Community tab. The ones you mark **featured** are
  the ones good enough for the front page.

> **An adult should do all of this.** It needs a Supabase account and a Google
> Cloud account, and once it is on you are storing other people's email
> addresses and publishing their links. There is a section at the bottom about
> what that means.

This guide assumes **REVIEWS-SETUP.md is already done** — same Supabase project,
same `supabase-config.js`. If it is not, do that one first; steps 1–3 there make
the accounts that this whole tab depends on.

## 1. Add the community table

Supabase dashboard → **SQL Editor → New query**. Paste all of this and press
**Run**.

```sql
-- Who is allowed to approve things. Everything below hangs off this one flag.
alter table public.profiles
  add column if not exists is_admin boolean not null default false;

-- Asking "is the person making this request an admin?" inside a policy would
-- read profiles from inside a policy on profiles, which recurses. A security
-- definer function steps outside that loop.
create or replace function public.is_admin()
returns boolean language sql security definer stable set search_path = '' as $$
  select coalesce((select p.is_admin from public.profiles p where p.id = auth.uid()), false);
$$;

create table public.community_games (
  id         bigint generated by default as identity primary key,
  author_id  uuid not null references public.profiles(id) on delete cascade,
  title      text not null check (char_length(title) between 2 and 60),
  tagline    text not null default '' check (char_length(tagline) <= 90),
  blurb      text not null default '' check (char_length(blurb) <= 600),
  -- https only. An http link is blocked by the browser inside an https page
  -- anyway, so it would just be a blank frame.
  url        text not null check (url ~ '^https://'),
  accent     text not null default '#5ce08a' check (accent ~ '^#[0-9a-fA-F]{6}$'),
  status     text not null default 'pending'
             check (status in ('pending', 'approved', 'rejected')),
  note       text not null default '' check (char_length(note) <= 200),
  featured   boolean not null default false,
  created_at timestamptz default now()
);

create index community_games_status_idx on public.community_games (status, created_at desc);

alter table public.community_games enable row level security;

-- Everyone sees approved games. You also see your own, whatever state they are
-- in, so you can tell whether yours is still waiting. Admins see everything.
create policy "approved games are public"
  on public.community_games for select
  using (status = 'approved' or author_id = auth.uid() or public.is_admin());

-- You may only put up a game as yourself, and only ever straight into the
-- queue. A browser cannot talk its way to 'approved'.
create policy "submit your own game"
  on public.community_games for insert
  with check (auth.uid() = author_id and status = 'pending' and featured = false);

-- Only an admin decides what is approved or featured.
create policy "admins moderate"
  on public.community_games for update
  using (public.is_admin()) with check (public.is_admin());

-- Authors can take their own game down; admins can take anything down.
create policy "delete your own game"
  on public.community_games for delete
  using (author_id = auth.uid() or public.is_admin());
```

### Replace the sign-up trigger

The trigger from REVIEWS-SETUP.md takes the username from the sign-up form.
Google never sends one, so signing in with Google would fail on a not-null
column. This version builds a username from the Google name or the email
address and adds a digit if it is taken.

```sql
create or replace function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = '' as $$
declare
  base text;
  try  text;
  n    int := 0;
begin
  -- Email sign-ups send a username. Google sends none, so make one.
  base := coalesce(
    nullif(new.raw_user_meta_data->>'username', ''),
    nullif(regexp_replace(split_part(coalesce(new.email, ''), '@', 1),
                          '[^a-zA-Z0-9_]', '', 'g'), ''),
    'player'
  );
  base := left(base, 16);
  if char_length(base) < 3 then base := 'player'; end if;

  try := base;
  while exists (select 1 from public.profiles where username = try) loop
    n := n + 1;
    try := base || n::text;
  end loop;

  insert into public.profiles (id, username) values (new.id, try);
  return new;
end;
$$;
```

## 2. Make yourself the admin

Sign in to the live site once with the account you want to moderate from, so the
account exists. Then, in **SQL Editor**, with your own username:

```sql
update public.profiles set is_admin = true where username = 'YOUR_USERNAME';
```

Sign out and back in on the site — the admin flag is read when you sign in.
The queue and the Approve / Reject buttons only appear for an admin.

## 3. Switch on "Continue with Google"

This is the part that needs a Google account as well as a Supabase one.

1. Go to <https://console.cloud.google.com> → create a project (any name).
2. **APIs & Services → OAuth consent screen.** Pick **External**, fill in the app
   name, your email, and save. While it is in *Testing* only accounts you list
   can sign in — press **Publish app** when you want it open to everyone.
3. **APIs & Services → Credentials → Create credentials → OAuth client ID.**
   - Application type: **Web application**
   - **Authorised redirect URI** — paste exactly this, with your own project ref:

     ```
     https://YOUR-PROJECT.supabase.co/auth/v1/callback
     ```

   Google gives you a **Client ID** and a **Client secret**.
4. In Supabase: **Authentication → Sign In / Providers → Google.** Turn it on and
   paste both values in. Save.
5. Still in Supabase: **Authentication → URL Configuration.** Set **Site URL** to
   `https://thirstybearstudios.com`, and add the same address under **Redirect
   URLs**. Without this Google sends people back to the wrong place after they
   sign in.

> Keep the **client secret** in Supabase only. It never goes in
> `supabase-config.js` — that file is published with the website.

## Why games are links and not uploads

Someone else's game is someone else's code. If it were uploaded here it would
run on this website's own address, and code running there can read everything
this site has stored in the browser — including the token that says you are
signed in. A single bad submission could quietly post as any visitor who played
it.

Keeping games on their author's own site means the worst a bad submission can do
is be a bad game. On top of that the player frame runs community games in a
locked-down `sandbox` with no `allow-same-origin`, so even a link that redirects
somewhere unexpected cannot reach anything of yours.

The trade-off: a community game **cannot save your progress** inside the frame.
The "open in its own tab" button in the player bar is there for that — on its own
site the game behaves completely normally.

## What you have taken on

**Every submission is yours to approve.** Nothing reaches the public tab on its
own. If you never look at the queue, nothing appears — which is the safe way
round.

**You are publishing links to other people's sites.** Check them. A link can be
edited by its owner after you approve it, so it is worth a look now and then at
anything popular. Delete removes it immediately.

**Rejecting is not deleting.** A rejected game stays visible to its author with
your note, so they know why. Delete it as well if you want it gone.

**People can take their own games down** without asking you.

**If someone asks you to delete their account,** deleting their row in `profiles`
takes their games and reviews with it.
